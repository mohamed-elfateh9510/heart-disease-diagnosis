# نظام تشخيص أمراض القلب باستخدام التعلم الآلي

## نبذة عن المشروع

المشروع ده بيهدف إلى التنبؤ باحتمال إصابة المريض بمرض القلب اعتمادًا على 11 معلومة طبية، زي العمر والجنس ونوع ألم الصدر وضغط الدم ومستوى الكوليسترول.

نفذت المشروع ده عشان أطبق مفاهيم التعلم الآلي على بيانات طبية حقيقية، وأتعلم إزاي أحول نموذج تم تدريبه إلى تطبيق بسيط يقدر المستخدم يتعامل معاه من خلال واجهة ويب أو API.

استخدمت التعلم الآلي (Machine Learning) بدلًا من التعلم العميق (Deep Learning)، لأن البيانات في المشروع عبارة عن جدول صغير نسبيًا، والنماذج التقليدية مناسبة للنوع ده من البيانات وأسهل في التدريب والتقييم.

## مميزات المشروع

* تنظيف البيانات وتحليلها باستخدام الرسوم البيانية.
* تدريب ومقارنة 5 نماذج مختلفة من نماذج التعلم الآلي.
* اختيار أفضل نموذج بناءً على نتائج التقييم.
* التنبؤ بحالة المريض وعرض الاحتمال الذي يتوقعه النموذج.
* إظهار تنبيه مبكر إذا تجاوز الاحتمال المتوقع 80%.
* عرض أقرب 3 مرضى مشابهين للمريض الحالي من بيانات التدريب.
* تنبيهات وتوصيات مبنية على بيانات المريض (ضغط الدم، الكوليسترول، `exang`، مؤشرات ST وتخطيط القلب)، وليس على نسبة التوقع فقط، مع تحديد أولوية المراجعة.
* سجل لكل مريض: حفظ كل زيارة، ومقارنة آخر زيارتين، وعرض تطور الاحتمال والقياسات مع الوقت.

## مجموعة البيانات

استخدمت مجموعة بيانات **UCI Heart Disease** المتاحة على Kaggle.

رابط البيانات: [Heart Disease Dataset على Kaggle](https://www.kaggle.com/datasets/redwankarimsony/heart-disease-data)

تحتوي مجموعة البيانات على 920 سجلًا للمرضى:

* 509 مرضى مصابين بأمراض القلب.
* 411 مريضًا غير مصابين بأمراض القلب.

## تجهيز البيانات وتنظيفها

قبل تدريب النماذج، جهزت البيانات ونفذت مجموعة من خطوات المعالجة:

* حذف الأعمدة غير الضرورية مثل `id` و`dataset`.
* تحويل العمود `num` إلى عمود الهدف `target`، بحيث تكون القيمة `0` لعدم وجود مرض القلب و`1` لوجود المرض.
* حذف العمودين `ca` و`thal` بسبب وجود عدد كبير من القيم المفقودة فيهما.
* التعامل مع القيم الصفرية في الكوليسترول وضغط الدم باعتبارها قيمًا مفقودة وفقًا لافتراضات التنظيف المستخدمة في المشروع.
* تقسيم البيانات إلى بيانات تدريب وبيانات اختبار قبل تدريب خطوات المعالجة، لتجنب تسريب المعلومات من بيانات الاختبار.
* استخدام خطوات لمعالجة القيم المفقودة داخل الـ Pipeline.

## تدريب النماذج وتقييمها

جربت 5 نماذج مختلفة، ثم قارنت أداءها باستخدام بيانات اختبار تتكون من 184 مريضًا لم تُستخدم في تدريب النماذج.

| النموذج             | الدقة (Accuracy) | الاستدعاء (Recall) |
| ------------------- | ---------------: | -----------------: |
| SVM                 |            83.7% |                92% |
| Random Forest       |            81.5% |                88% |
| Logistic Regression |            79.3% |                84% |
| KNN                 |            78.8% |                85% |
| Decision Tree       |            76.6% |                81% |

اخترت نموذج **SVM** باعتباره النموذج النهائي، لأنه حقق أفضل نتائج بين النماذج التي تمت مقارنتها في التجربة.

بحسب نتائج الاختبار، اكتشف النموذج 94 حالة من أصل 102 حالة مصابة بمرض القلب، بينما لم يكتشف 8 حالات مصابة. كما أعطى إنذارًا إيجابيًا خاطئًا لـ22 مريضًا غير مصاب.

بلغت قيمة **ROC-AUC** للنموذج 0.889.

اهتممت بمقياس Recall لأنه يوضح نسبة الحالات المصابة التي استطاع النموذج اكتشافها. وفي مشروع طبي، من المهم تقليل الحالات المصابة التي قد يفشل النموذج في اكتشافها، مع مراعاة أن الإنذارات الخاطئة لها أهمية أيضًا.

## هيكل المشروع

```text
heart-disease-diagnosis/
│
├── data/
│   └── heart_disease_uci.csv
│
├── notebooks/
│   └── medical_diagnosis.ipynb
│
├── src/
│   └── train.py
│
├── models/
│   └── heart_disease_pipeline.pkl
│
├── src/alerts.py        (قواعد التنبيهات وأولوية المراجعة)
├── src/records.py       (سجل المرضى والزيارات في SQLite)
├── src/model_io.py      (تحميل النموذج مع التحقق من إصدار scikit-learn)
├── tools/check_model_version.py
├── api.py
├── app.py
└── requirements.txt
```

توضيح الملفات:

* `data/`: يحتوي على ملف البيانات المستخدم في المشروع.
* `notebooks/medical_diagnosis.ipynb`: يحتوي على تحليل البيانات والرسوم وتجربة النماذج وتقييمها.
* `src/train.py`: مسؤول عن تدريب النموذج النهائي وحفظه.
* `models/heart_disease_pipeline.pkl`: يحتوي على الـ Pipeline المحفوظ للاستخدام بعد التدريب.
* `app.py`: يحتوي على واجهة الويب باستخدام Streamlit.
* `api.py`: يحتوي على واجهة API باستخدام Flask.
* `requirements.txt`: يحتوي على المكتبات المطلوبة لتشغيل المشروع.

## طريقة تشغيل المشروع

### 1. إنشاء بيئة افتراضية

```bash
python -m venv venv
```

لتفعيل البيئة على Windows:

```bash
venv\Scripts\activate
```

### 2. تثبيت المكتبات المطلوبة

```bash
pip install -r requirements.txt
```

### 3. تدريب النموذج وحفظه

```bash
python -m src.train
```

الخطوة دي بتشغل كود التدريب وتحفظ النموذج النهائي لاستخدامه في التطبيق.

### 4. تشغيل واجهة الويب

```bash
streamlit run app.py
```

بعد التشغيل، يفتح Streamlit التطبيق في المتصفح.

### 5. تشغيل الـ API

```bash
python api.py
```

تكون الخدمة متاحة محليًا على العنوان:

`http://127.0.0.1:5000`

لتشغيل ملف تحليل البيانات والنماذج:

```bash
jupyter notebook notebooks/medical_diagnosis.ipynb
```

## واجهة الويب باستخدام Streamlit

تتيح الواجهة للمستخدم إدخال البيانات الطبية للمريض، ثم الضغط على **Analyze Patient** للحصول على النتيجة.

تعرض الواجهة:

* النتيجة المتوقعة لحالة المريض.
* الاحتمال الذي يتوقعه النموذج للإصابة بمرض القلب.
* تنبيهًا مبكرًا إذا تجاوز الاحتمال نسبة 80%.
* أقرب 3 مرضى مشابهين من بيانات التدريب.

يمكن التعامل مع المعلومات غير المعروفة من خلال ترك الحقول اختيارية أو اختيار `Unknown`، بشرط أن تكون الواجهة وكود المعالجة مجهزين للتعامل مع القيم المفقودة.

## استخدام Flask API

أضفت API حتى يمكن إرسال بيانات المريض واستقبال نتيجة النموذج دون الحاجة إلى استخدام واجهة Streamlit.

| المسار     | الطريقة | الوظيفة                                |
| ---------- | ------- | -------------------------------------- |
| `/health`  | GET     | التأكد من أن الخدمة تعمل               |
| `/predict` | POST    | إرسال بيانات المريض والحصول على التنبؤ |


## توحيد إصدار scikit-learn

النموذج المحفوظ (`models/heart_disease_pipeline.pkl`) أُنشئ بـ scikit-learn **1.6.1**، بينما كان `requirements.txt` يحدد `<1.6`. وُحّد الإصدار بتثبيت `scikit-learn==1.6.1` في `requirements.txt`، دون الحاجة لإعادة بناء النموذج. أعيد التدريب للتأكد فكانت النتائج مطابقة (Accuracy 0.837 وROC-AUC 0.8886)، واحتمالات النموذج المعاد تدريبه تطابق المحفوظ.

للتحقق في أي بيئة:

```bash
pip install -r requirements.txt
python tools/check_model_version.py
```

السكربت يطبع إصدار النموذج والبيئة و`requirements.txt` ويفشل لو اختلفت. كما أن `api.py` و`app.py` يحمّلان النموذج عبر `src/model_io.py`، فيتوقفان برسالة واضحة بدل إعطاء نتائج قد تكون خاطئة عند اختلاف الإصدار. وإن غيّرت الإصدار مستقبلًا فأعد التدريب بـ `python -m src.train`.

## التنبيهات والتوصيات

كل تنبؤ يرجع أولوية مراجعة (`urgent` / `high` / `moderate` / `routine`) وقائمة تنبيهات، من القواعد التالية:

| المؤشر | التنبيه |
| ------ | ------- |
| ضغط الدم ≥ 140 (≥ 180 حرج) | متابعة ضغط الدم |
| الكوليسترول ≥ 240 | مراجعة مستوى الدهون |
| `exang` = true | تقييم إضافي للطبيب (مثل اختبار الجهد) |
| `oldpeak` ≥ 2، أو ميل ST هابط، أو تخطيط قلب غير طبيعي | تقييم قلبي إضافي |
| سكر الصائم > 120 | فحص مستوى السكر |
| احتمال الخطر ≥ 80% (≥ 50% مرتفع) | رفع أولوية المراجعة |

القيم غير المعروفة لا تطلق تنبيهًا، ويُذكر أنها ناقصة. الحدود تعليمية وبسيطة ويمكن تعديلها في `src/alerts.py`، وهي مساندة للطبيب وليست تشخيصًا.

## سجل المريض ومتابعة الزيارات

- في Streamlit: اكتب **Patient ID** (مثل `P001`، وليس الاسم الحقيقي) قبل الضغط على Analyze لحفظ الزيارة، ثم افتح تبويب **Patient history** لرؤية الزيارات ومنحنى التطور والمقارنة مع الزيارة السابقة.
- في الـ API: أرسل `patient_id` (و`visit_date` اختياريًا بصيغة `YYYY-MM-DD`) مع `/predict` لحفظ الزيارة.

| المسار | الطريقة | الوظيفة |
| ------ | ------- | ------- |
| `/patients` | GET | المرضى المسجلون وعدد زياراتهم |
| `/patients/<id>/history` | GET | كل زيارات المريض بالترتيب الزمني |
| `/patients/<id>/compare` | GET | مقارنة آخر زيارتين (الاحتمال، الضغط، الكوليسترول، ...) |

البيانات تُحفظ في `data/patients.db` (SQLite)، ولا تُرفع إلى git. لتغيير المسار استخدم المتغير `HEART_DB_PATH`.

## حدود المشروع

* سجل المرضى غير مؤمّن (لا تسجيل دخول ولا تشفير)، وهو لأغراض العرض فقط ولا يصلح لبيانات مرضى حقيقية.

* حجم البيانات محدود نسبيًا، لذلك قد تختلف النتائج عند استخدام بيانات من مرضى آخرين.
* لم يتم التحقق من أداء النموذج على مجموعة مستقلة من مرضى مستشفى خارج المستشفيات الموجودة في البيانات.
* أخفق النموذج في اكتشاف 8 حالات من أصل 102 حالة مصابة ضمن نتائج الاختبار المذكورة.
* الاحتمال الذي يعرضه النموذج ليس بالضرورة تقديرًا طبيًا معايرًا لاحتمال إصابة المريض الفعلي.
